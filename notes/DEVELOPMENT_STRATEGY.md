# DEVELOPMENT_STRATEGY.md：开发策略建议

> 2026-05-19 更新：本文主要记录 V0.1 风光储技术测算模块初期开发策略。项目当前已升级规划为“绿电直连 / 微电网项目方案策划与推荐平台”。后续开发请优先参考 `AGENTS.md`、`CLAUDE.md` 和 `notes/architecture_reframe_20260519/`。本文中“不建议擅自加入经济性模块”等说法适用于 V0.1 初期基线阶段，不再作为未来产品边界。

## 1. 能否自动化完成初版开发？

可以高度自动化，但不建议“一句话一口气完成”。

原因：

1. 本项目核心风险是算法口径错误，不是代码量大；
2. AI 容易把储能损耗、弃电、自发自用等口径混在一起；
3. AI 容易忽略 SOC 跨小时滚动；
4. AI 容易擅自加入经济性模块，导致当前阶段复杂化；
5. AI 容易写出能跑但不可复核的结果。

因此建议：

```text
文档锁定需求 → 分阶段提示 → 每阶段测试 → 人工抽查结果 → 下一阶段
```

## 2. 推荐开发模式

### Claude Code

适合：

- 理解长文档；
- 持续迭代；
- 修改代码；
- 做界面；
- 解释错误。

使用 CLAUDE.md 作为项目记忆文件。

### Codex

适合：

- 按 AGENTS.md 执行工程任务；
- 写测试；
- 修 bug；
- 重构；
- 生成代码补丁。

使用 AGENTS.md 作为 agent 指令文件。

## 3. 初期不要开启过高权限

在项目尚未稳定前，不建议使用完全放开的 YOLO 模式。

建议：

- 允许读写项目目录；
- 允许运行 pytest；
- 允许运行 streamlit；
- 对删除文件、批量重构、安装未知依赖保持谨慎。

## 4. 人工必须复核的地方

1. 储能是否只从新能源充电；
2. SOC 是否跨小时滚动；
3. 储能损耗是否单独统计；
4. 自发自用率公式是否正确；
5. 上网比例是否为年度积分；
6. 8760 / 8784 是否都能跑；
7. 导出的逐小时明细是否可人工追溯。
