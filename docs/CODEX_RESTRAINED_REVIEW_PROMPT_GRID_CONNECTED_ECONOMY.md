# Codex 克制型提示词：并网型风光储经济性与推荐排序现状审查

> 使用方式：把本文件放到项目 `docs/` 目录，或直接复制其中“给 Codex 的提示词”到 Codex。
>
> 目标：避免 Codex 在不了解项目现状的情况下重复造轮子、重构已有功能、扩大范围。

---

## 给 Codex 的提示词

```text
请你在当前项目仓库中做一次“并网型风光储经济性、政策筛选、推荐排序、图表分析”的现状审查和下一步建议。

重要前提：

1. 我已经完成了并网型风光储方案枚举和逐小时调度基座。
2. 项目里可能已经实现了经济性、政策筛选、推荐排序、图表、导出、UI、测试等很多功能。
3. 你不能假设这些功能不存在。
4. 本轮不要直接大规模改代码。
5. 本轮首要任务是：审查已有能力、识别缺口、避免重复建设、提出最小下一步方案。

一、请先审查项目现状

请扫描项目结构，尽量找出以下内容实际在哪里：

- 风电、光伏、储能容量枚举入口；
- 单方案计算入口；
- 当前并网调度策略；
- hourly_detail / 小时台账 / HourlyEnergyLedger 等逐小时结果；
- summary / ScenarioResult / BatchResult 等结果对象；
- 政策指标计算逻辑；
- 政策筛选逻辑；
- 经济性计算逻辑；
- IRR、NPV、CAPEX、OPEX、回收期等指标是否已有；
- 排序、推荐、筛选、方案对比逻辑；
- 用户指定方案或手动添加方案能力是否已有；
- 图表分析模块；
- 导出模块；
- UI 入口；
- 测试文件和测试命令。

请输出一个表格：

| 模块 | 是否已发现 | 相关文件/函数 | 当前能力 | 可能缺口 | 是否建议本轮修改 |
|---|---|---|---|---|---|

如果没有找到某个模块，请写“未发现”，不要自行假设不存在。

二、请判断是否存在重复建设风险

重点检查：

- 是否已经有政策筛选对象或函数；
- 是否已经有经济性结果结构；
- 是否已经有推荐排序逻辑；
- 是否已经有图表读取结果的机制；
- 是否已经有用户自定义方案或指定方案能力；
- 是否已经有测试覆盖这些功能。

如果已有功能，请优先建议“复用、整理、补测试、补说明”，不要新建一套平行系统。

三、当前产品主线

当前阶段只聚焦并网型风光储：

枚举方案
→ 当前并网调度策略计算小时台账
→ 政策指标硬筛选，阈值可调
→ 对达标方案计算经济性
→ 按推荐取向排序
→ 系统推荐方案 + 用户指定方案参与对比
→ 后续图表解释方案差异

不要把柴发、离网、弱网、电价驱动优化调度混入本轮。

四、已确认的业务规则

政策筛选是硬筛选，但阈值应可调。

默认政策阈值可以包括：

- 年上网电量 / 总可用发电量 ≤ 20%
- 项目自身新能源整体年消纳电量 / 总可用发电量 ≥ 60%
- 项目自身新能源整体年消纳电量 / 项目总用电量 ≥ 30%
- 可允许用户改为 35% 或其他值

经济性评价默认只读取调度结果和经济参数，不改变小时台账，不重新计算 SOC、上网、下网、弃电、储能充放电。

电价驱动储能优化调度是未来拓展功能，应作为独立 DispatchStrategy 或独立高级页面，不影响当前默认并网基座。

推荐排序取向暂定为：

1. 经济性最优：IRR 最大；
2. 投资最少：CAPEX 最小；
3. 弃电最少：弃电量或弃电率最小；
4. 储能最小：储能容量最小，必要时兼顾储能功率和储能电量；
5. 均衡推荐：暂时占位，不要强行设计复杂评分模型。

推荐结果需要去重，但保留推荐标签。

用户指定方案参与对比的目标是：让用户输入自己关心的风光储配置，按同一套调度、政策、经济性流程计算，并与系统推荐方案对比。若项目中已有类似能力，请复用；若没有，本轮先提出最小设计，不要强行大改 UI。

五、本轮不要做的事情

不要实现：

- 柴油发电机模型；
- 离网风光储柴；
- 弱网复杂调度；
- Load Following；
- Cycle Charging；
- Combined Dispatch；
- MILP；
- 电价驱动储能优化调度；
- 多用户内部结算；
- 用户级绿电分摊；
- 大规模 UI 重写；
- 大规模架构推倒重来；
- 与现有模块平行的新经济性系统；
- 与现有模块平行的新推荐系统。

六、请输出审查报告，而不是直接开工

请先输出：

1. 项目现状审查表；
2. 已有能力总结；
3. 缺口清单；
4. 重复建设风险；
5. 建议保留不动的模块；
6. 建议轻微整理的模块；
7. 建议新增或补强的最小内容；
8. 推荐的测试补充；
9. 如果要进入开发，下一步最小任务卡是什么；
10. 需要我确认的问题。

在我确认前，不要进行大规模修改。

如果你认为某些小改动可以直接做，必须说明：

- 为什么不会影响当前默认计算结果；
- 为什么不会重复已有功能；
- 修改哪些文件；
- 如何回滚；
- 如何测试。
```

---

## 本提示词的核心约束

```text
先审查，后开发。
先复用，后新增。
先补测试，后扩功能。
先保护现有并网基座，后考虑拓展模式。
不要假设项目缺功能。
不要重构整个世界。
```
