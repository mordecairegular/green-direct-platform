# Product Design UI Audit Report

审计日期：2026-06-06

目标：全面审阅当前项目模块、Streamlit UI、交互流程、图表和导出体验，形成不触碰底层计算逻辑的 UI 改造依据。

范围边界：本报告只评价 UI 展示层、交互组织、信息架构、视觉层级、空状态、错误状态、图表表达和导出体验。底层技术仿真、储能调度、经济性计算和推荐排序口径不在本轮改造范围内。

## Executive Diagnosis

当前 UI 已经从“全量枚举表工具”推进到“六步工程工作台”，大方向是对的。最有价值的进展是：推荐页开始承接决策，图表页开始围绕代表方案复核，导出动作集中到最后一页。

主要瓶颈不再是单纯“丑”，而是任务分层还没有完全收口：参数、状态、解释、执行按钮和复核信息仍在长页面里混杂。用户知道下一步该点哪里，但不一定知道每页要完成什么判断。

最优先要改的是信息架构和交互节奏，其次才是视觉样式。现阶段不建议重写底层逻辑或更换技术栈；应该先把 Streamlit 工作台整理成稳定的 UI 表面契约，再逐步抽出组件。

## Page Findings

### 1. 欢迎页

证据：`screenshots/01-welcome.png`

优点：

- 六步工作流清楚，符合当前产品方向。
- 顶部状态条把项目、模块、流程状态、方案池和数据时间放到同一层。
- 不再把全量枚举表作为主入口。

问题：

- 欢迎页像说明页，缺少“项目启动台”的实用性。可以更直接展示：当前是否有曲线、是否有候选池、推荐/导出是否可用、下一步 CTA。
- 顶部状态条和左侧状态卡信息有重复，用户要读两遍才能理解状态。
- 卡片和说明文字比例偏大，首屏没有形成“我现在能做什么”的强行动线。

### 2. 方案仿真页

证据：`screenshots/02-simulation-initial.png`、`screenshots/14-flow-simulation-after-demo.png`

优点：

- 输入、候选方案池、政策约束三列结构可读。
- Demo 路径能生成 27 个方案、22 个达标，适合演示完整闭环。
- 完成后左侧和顶部状态会更新。

问题：

- “数据曲线”区仍偏表单堆叠，尚未变成输入诊断台。用户更需要看到缺失项、识别结果、单位和异常，而不是先看到上传控件。
- 候选方案池以参数网格为主，但没有显式说明枚举只是内部搜索方法。
- 政策约束和电网约束没有形成“达标门槛”摘要。
- Demo 生成按钮和正式开始测算按钮并列，但 Demo 的用途、是否覆盖当前输入、是否清空旧经济结果，需要更明确。

### 3. 经济性测算页

证据：`screenshots/15-flow-economy-before-run.png`、`screenshots/26-economy-after-run.png`

优点：

- 已把经济性前置为独立页面，方向正确。
- 基本参数、建设投资、费用、储能更换、收入税金等字段与当前经济口径基本一致。
- 未上传项目级下网电价曲线时有清楚提示。

问题：

- 首屏几乎全是参数，用户看不到“计算经济性 V1”的主动作。按钮在 DOM 中位于下方，审计脚本需要定位 `V1` 才能点击。
- 常用字段和高级字段还没有足够分层。比如默认用户更需要先确认净避免购电成本、绿电结算价、最低可接受 FIRR、基础 capex，而不是读完整经济参数清单。
- 经济计算完成后页面仍停在参数顶部，缺少结果摘要回馈。成功提示有了，但用户需要立即看到“哪些席位可排序、哪个方案暂领先、哪些字段缺失”。
- 参数表单缺少分步保存或“已改动未重算”状态，容易让用户误以为输入后结果自动更新。

### 4. 方案推荐页

证据：`screenshots/16-flow-recommendation-before-economy.png`、`screenshots/27-recommendation-after-economy.png`

优点：

- 推荐页已经只做决策，默认展示代表方案卡片，不再主推全量枚举表。
- 一张方案可合并多个推荐席位，符合产品原则。
- 推荐页底部显示默认报告方案、逐小时台账数量和数据来源。

问题：

- 推荐卡片理由在卡片内被截断，用户无法完整判断为什么推荐。
- 席位名称需要更像决策语言。例如“同一主体 FIRR 最优；电源侧 FIRR 最优”可以保留，但要配一句业务解释。
- 风险提示分级不足。当前有“已入选”状态，但缺少 `warning / pending / no_candidate` 的显著视觉差异。
- 高级明细折叠是对的，但缺少“展开后能复核什么”的微文案。

### 5. 图表概览页

证据：`screenshots/17-flow-chart-before-economy.png`、`screenshots/28-chart-after-economy.png`

优点：

- 默认图表围绕推荐组合和指定方案，不再围绕全量枚举。
- “多方案关键指标对比”和“容量配置横向对比”是合适的主图。
- 图例包含方案编号和容量配置，便于与推荐卡片互相映射。

问题：

- 图表页的定位应该是复核，而不是第二个推荐页。当前标题已经接近，但每张图还应明确回答一个问题：为什么它更经济、为什么自用率高、为什么弃电低。
- 指定方案选择和推荐方案选择并列，但用户很难知道“加入指定方案”会影响哪些图表。
- 高级区包含典型日、能量流和完整图表分析，方向正确，但需要更明确的图表分组：方案对比、典型日、关键日、能量流、导出准备。

### 6. 下载报告页

证据：`screenshots/18-flow-export-before-economy.png`、`screenshots/29-export-after-economy.png`

优点：

- 下载动作集中到一个页面，避免仿真、经济、推荐页按钮散落。
- 默认报告方案自动选择推荐组合首个方案 `S0010`。
- 技术数据、图表包、经济与报告三列结构清楚。

问题：

- 交付中心还缺少“包”的概念。用户需要知道将要交付的是技术包、经济表、图表包、简版报告还是完整审计包。
- 图表 HTML ZIP 需要勾选准备，说明了成本，但还可以显示预计包含哪些图、是否仅含推荐组合。
- 报告页没有显示“缺少项”汇总。例如 PNG 批量导出尚未接入、年度现金流是否已可导出、推荐组合是否已重新构建。

## Visual And Interaction Findings

P0 问题：

- 窄屏不可用。`screenshots/30-mobile-welcome.png` 和 `screenshots/31-mobile-simulation.png` 显示左侧导航覆盖主内容，顶部状态条和卡片被截断。
- 经济性主 CTA 不在首屏，且参数页完成后没有结果摘要区域。

P1 问题：

- 顶部状态条和左侧状态卡重复，建议改为“顶部项目状态 + 左侧流程导航 + 页面内任务状态”三层分工。
- 全局 CSS 和页面渲染集中在 `app.py`，视觉调整容易牵动大文件。
- 图表 CSS 在 `chart_ui.py` 内自成一套，与主工作台 CSS 并行，后续容易出现卡片、间距、颜色不一致。
- 成功、警告、待处理、不可计算状态还没有统一视觉语义。

P2 问题：

- 卡片圆角、边框、阴影、按钮大小基本可接受，但整体仍偏 Streamlit 默认控件质感。
- 参考图的高密度 dashboard 气质可以借鉴，但不应照抄其 mock 字段。

## Accessibility Notes

- 窄屏布局当前不通过，移动端和小窗口用户会被遮挡。
- 当前没有完成键盘导航、焦点态和屏幕阅读器审计。
- 状态依赖颜色和小圆点，建议同时保留文字标签。
- 多图表颜色需要检查色盲可辨性，尤其是蓝、绿、橙组合。
- 推荐理由截断后需要可展开文本或详情区，不能让关键信息只停留在 tooltip 或隐藏表格中。

## Streamlit Constraint Vs. Product Organization

Streamlit 限制：

- 原生控件样式和 DOM 层级难以完全控制。
- 多页面状态依赖 `st.session_state` 和 rerun，按钮跳转需要 pending key 方案。
- 长表单滚动、下载按钮准备和图表渲染容易触发重复 rerun。

可通过产品组织解决的问题：

- 每页只承载一个主任务。
- 推荐页只做决策，图表页只做复核，导出页只做交付。
- 把高级复核和全量表格收进折叠区或导出包。
- 建立共享 UI token 和组件边界，减少全局 CSS 竞争。

## Audit Limits

- 本轮未修改正式代码，因此未运行全量 pytest。
- 截图取证使用本地 Chromium/Playwright fallback；Codex in-app Browser 在当前环境无法启动。
- 自动化读取中文文本有编码噪声，但截图渲染正常。
- 本轮没有验证真实用户上传 CSV 的全部异常路径，只验证了 Demo 主流程和默认经济参数路径。
