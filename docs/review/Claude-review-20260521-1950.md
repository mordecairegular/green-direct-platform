## 一、项目理解

你在做的是**绿电直连/微电网配置规划与方案推荐平台**，面向绿电直连项目前期策划场景。

核心问题：给定负荷曲线、光伏/风电出力曲线、政策约束和经济参数，枚举风光储配置方案、逐小时仿真、筛选可行方案、给出有理由的推荐方案组合。

V0.1 是一个批量测算工具（输入 → 全量枚举 → 输出大表），目标产品是在这个基础上加入筛选-排序-推荐-报告层，让用户不需要自己解读几百行枚举表。理解准确。

### 具体代码级问题

**问题1：`batch_runner.py:80-91` 的排序不是推荐**

```python
summary = summary.sort_values(
    by=["pass_policy", "green_load_rate", "self_use_rate", ...],
    ascending=[False, False, False, True, True, True],
)
```

这是排序，不是推荐。没有理由、没有多样性控制、没有代表方案筛选。这是产品Gap最集中的地方——整个"平台"愿景到这里断掉了。

**问题2：`economic_evaluator.py:299`，BESS运维成本口径**

```python
bess_om_cost_with_vat = bess_power * economic_params.bess_om_cost_per_kw_year
```

按功率容量（kW）计提。行业更常见的是按能量容量（kWh）计提。UI标签也写的"储能运维成本（元/kW/年）"。如果批量场景里时长变化范围大（如1h vs 4h），这个口径会影响经济排序结论。这是算法选择不是bug，但需要意识到并在报告中说明。

**问题3：`economic_evaluator.py:327-336`，折旧年限硬编码**

```python
if operation_year <= 20:
    wind_depreciation = wind_depreciation_basis / 20
    ...
```

折旧年限20年硬编码在函数体内。应成为 `EconomicParams` 的字段。

**问题4：`economic_evaluator.py:276-415`，收入逐年不变**

`grid_export_energy` 和 `self_use_energy` 从技术仿真读一次，然后每个运营年用相同的数。光伏年衰减约0.5%/年，25年累积差约12%。对规划初筛可接受，但需在报告中说明这个简化假设。

**算法正确性确认：**

- `metrics.py:95`：`annual_equivalent_cycles = bess_discharge_to_load / bess_energy`——公式正确
- `single_scenario_simulator.py:274`：SOC用 `±1e-12` 容差处理浮点边界——正确且有意为之
- 站用电（负PU值）处理——正确，负值计入自耗，不记入发电

## 三、方法科学性评价

### 总体：科学合理，是行业标准做法，无结构性错误

**调度策略**：贪心策略（新能源优先→直供负荷→充储→上网/弃电）是配置规划类工具的标准做法。规划工具不需要全局最优调度，贪心策略在年度汇总层面与最优调度差异很小，足够支撑方案比选。

**能量平衡**：站用电处理正确，许多工具在这里出错。

**BESS约束**：SOC边界、功率限制、充放电不同时、不从电网充电、不放电上网——全部正确实现。

**经济性模型**：框架完整，覆盖增值税进项留抵（逐年滚动）、固定资产折旧、储能换电、城建税及附加、所得税（含亏损结转）、FNPV/FIRR/回收期。在前期规划场景是够用的。

**架构分层**：仿真层只写事实，经济层只读仿真结果，图表层只读数据。没有逆向耦合。执行干净。

## 五、路径有无致命伤

**无致命伤。有三个值得关注的风险点。**

**风险1（最重要）：推荐引擎缺位**

产品定位是"方案推荐平台"，但目前没有推荐引擎——只有全量枚举表。用户拿到的还是几百行数据，需要自己解读。推荐引擎（筛选→经济排序→选代表方案→给理由）是整个产品价值的核心，也是技术难度最高的部分，尚未开始。

**风险2（中期）：大批量内存压力**

`BatchResult.hourly_details` 是全部方案逐小时 DataFrame 的 dict，全部在内存。100方案可接受，1000方案有压力，10000方案会OOM。文档有意识到，计划做summary-in-RAM + hourly-on-disk。在推荐引擎完成之前不急，但扩大规模前必须解决。

**风险3（未来）：柴发和离网实现复杂度**

柴发调度涉及能源来源标记——柴发给储能充电的电量不能计入新能源自发自用。文档（`04_HOURLY_DISPATCH_LOGIC_WITH_DIESEL.md`）对此有清醒认识。实现时字段设计出错会破坏绿电口径，是未来最需要小心的地方。

## 七、文档体系评价

### 总体判断

**认真做了，但已经变成负担，而不是资产。**

约50个markdown文件，问题不是数量多，而是：

**问题1：AI构建痕迹没有清理**

`prompts/`（8个文件）是当时驱动Codex建项目的提示词，项目建完就应该清掉。`docs/CODEX_*.md`（3个文件）是AI任务规格说明书，用完即删。这类文件留在活跃路径上，让人困惑"这是现状还是历史"。

`CLAUDE.md`、`AGENTS.md`、`notes/HANDOFF_FOR_NEW_MACHINE.md` 三个文件面向AI代理，内容高度重叠。每次更新要同步三个地方，必然产生漂移。

图表模块自认是临时原型，但有5个文档支撑（`PRD_CHART_MODULE.md` 376行、`CHART_MODULE_CONTRACT.md` 427行等）合计1200+行。与其重要性严重不匹配。
